## What it is
Demand paging is a virtual memory management technique where the operating system brings a page of data from secondary storage (like a hard disk) into main memory (RAM) only when a program tries to access it. This access attempt on a non-resident page triggers a hardware trap called a page fault, which signals the OS to load the required page. This "lazy loading" avoids loading an entire program into memory before it runs.

## Why it matters
This concept is the foundation of how modern computers run programs larger than their physical RAM. For large-scale scientific simulations, such as computational fluid dynamics for rocket engine analysis or N-body simulations in astrophysics, the datasets can be terabytes in size. Demand paging allows these programs to execute on machines with far less RAM by keeping only the actively used portions of the data in memory. Similarly, training large machine learning models often involves datasets that do not fit in memory; the data loading pipelines effectively use demand paging principles to feed data to the GPU.

## When to study it
Before tackling this, you must have a solid grasp of the following. If these are not clear, pause and review them.
*   **Virtual Memory:** The distinction between the logical address space generated by the CPU and the physical address space of main memory.
*   **Paging Hardware:** How the Memory Management Unit (MMU) translates a virtual address to a physical address using page tables.
*   **Page Table Structure:** The concept of a Page Table Entry (PTE) and, crucially, the purpose of the **valid-invalid bit**.
*   **Interrupts and Traps:** The mechanism by which hardware can interrupt the CPU and transfer control to a specific OS kernel routine (an interrupt handler).

## How to study it (step by step)
1.  **Review the Page Table Entry (PTE):** Draw a diagram of a PTE. Label the key fields: Frame Number and the Valid-Invalid bit. Convince yourself that the Valid-Invalid bit is the trigger for everything that follows. If it's 'valid', the frame number is good. If it's 'invalid', the page is not in memory.
2.  **Trace a "Happy Path" Memory Access:** Diagram the steps for a memory access where the page *is* in memory. CPU generates virtual address -> MMU splits it into page number ($p$) and offset ($d$) -> MMU uses $p$ to index the page table -> MMU finds the PTE, sees the valid bit is 1 -> MMU takes the frame number ($f$) from the PTE -> MMU combines $f$ and $d$ to form the physical address -> MMU fetches data from RAM.
3.  **Trace the Page Fault Path:** Now, repeat the trace, but this time assume the valid bit is 0. Write down, in order, what must happen. Don't worry about perfection; just think logically. What does the hardware do? What must the software (OS) do to fix the problem?
4.  **Introduce Scarcity:** Redo the trace from step 3, but now assume there are no free frames in physical memory. What new problem does the OS have to solve? This will lead you directly to the need for a *page replacement algorithm*.
5.  **Quantify the Cost:** Derive the formula for Effective Access Time (EAT). Let $t_{mem}$ be the time for a normal memory access and $p$ be the probability of a page fault. Let $t_{fault}$ be the time to service a page fault. The EAT is a weighted average: $EAT = (1-p) \cdot t_{mem} + p \cdot t_{fault}$. Calculate the EAT for typical values (e.g., $t_{mem}=100$ ns, $t_{fault}=10$ ms, $p=0.0001$). This shows why a low page fault rate is critical.

## Key ideas, with intuition
1.  **A Fault is a Feature, Not a Bug:** The term "fault" is misleading. A page fault is not a program error like a segmentation fault. It is a planned, routine hardware event (a trap) that tells the OS, "The data this program needs isn't in RAM. It's your job to go get it."
2.  **The Valid-Invalid Bit is the Gatekeeper:** The entire mechanism hinges on one bit per page in the page table. The hardware (MMU) is simple: it checks this bit. If `valid`, it proceeds. If `invalid`, it gives up and traps to the OS. The OS's job is to do the complex work, then flip the bit to `valid` and let the hardware try again.
    $$
    \text{PTE} = \{\underbrace{\text{Frame Number}}_{\text{Where in RAM}}, \underbrace{\text{Valid Bit}}_{\text{Is it in RAM?}}, \dots \}
    $$
3.  **Transparency is the Goal:** The entire, complex sequence of handling a page fault is designed to be completely invisible to the faulting program. The OS saves the program's state, handles the fault, restores the state, and restarts the *exact same instruction* that caused the fault. This time, the memory access succeeds, and the program continues as if nothing happened.
4.  **The Immense Time Penalty:** A normal memory access is measured in nanoseconds ($10^{-9}$ s). Accessing a disk is measured in milliseconds ($10^{-3}$ s). A page fault requires disk I/O, so it's millions of times slower than a normal memory access. This is why operating systems work very hard to predict which pages a program will need soon (locality of reference) to minimize faulting.

## Worked example
A program executes the instruction `LOAD R1, 1234`, where `1234` is a virtual address. The page size is 1KB (1024 bytes). The virtual address `1234` corresponds to page number $p = \lfloor 1234 / 1024 \rfloor = 1$ and offset $d = 1234 \pmod{1024} = 210$. The page table shows that page 1 is not in memory (valid bit = 0).

Here are the step-by-step actions:

1.  **Address Translation Attempt:** The CPU sends virtual address `1234` to the MMU. The MMU looks up the PTE for page 1 in the current process's page table.
2.  **Hardware Trap:** The MMU finds the PTE for page 1 and sees the valid bit is set to 0 ('invalid'). It cannot proceed. The MMU triggers a hardware trap (a page fault exception) to the OS, passing control to the kernel's page fault handler. The CPU state (program counter, registers) is saved.
3.  **OS: Validate Address:** The OS handler first checks its own internal tables (e.g., in the Process Control Block) to determine if virtual address `1234` is a legal address for this process. If not, it terminates the process (segmentation fault). In our case, it's a legal address for a page that just happens to be on disk.
4.  **OS: Find a Free Frame:** The OS looks at its list of free physical memory frames. Let's say it finds that frame 25 is free.
5.  **OS: Schedule Disk I/O:** The OS issues a command to the disk controller to read page 1 from its location in the swap space (e.g., on the hard disk) and load it into physical frame 25.
6.  **Wait and Context Switch:** This disk read is slow. The OS will likely context-switch to run another process while the disk I/O completes. When the disk controller finishes, it sends a hardware interrupt to the CPU.
7.  **OS: Update Page Table:** Upon receiving the disk I/O completion interrupt, the OS updates the process's page table. It sets the valid bit for page 1 to 1 ('valid') and writes the frame number, 25, into the PTE.
8.  **Restart Instruction:** The OS restores the saved state of the original process and returns control to it. The instruction `LOAD R1, 1234` is executed *again* from the beginning.
9.  **Success:** This time, when the CPU sends `1234` to the MMU, the MMU finds the PTE for page 1, sees the valid bit is 1, retrieves frame number 25, calculates the physical address (25 * 1024 + 210), and fetches the data successfully. The program continues, unaware of the complex dance that just occurred.

*Reflection:* Each step is a logical necessity. The hardware detects the problem (2), the OS validates the request (3), allocates resources (4), performs the slow operation (5), updates its records (7), and finally lets the original request retry (8).

## Memory technique — remember this forever
1.  **The Librarian Analogy:** Think of memory access as asking a librarian for a book.
    -   You (the CPU) ask for a book by its title (virtual address).
    -   The librarian (MMU) checks the card catalog (page table).
    -   **Normal Case:** The card says "Section 7, Shelf 3" (valid bit=1, frame=7). The librarian gets it. Fast.
    -   **Page Fault:** The card says "In Deep Archives" (valid bit=0). This is a special request! The librarian triggers a **TRAP**.
    -   A page (the OS) runs to the archives (disk), finds the book, brings it back, finds an empty spot on a shelf (free frame), and updates the card catalog with the new location.
    -   The page tells the librarian, who then tells you to ask for your book again. This time, it works.
2.  **Must-Know Formula:** The Effective Access Time (EAT). You must be able to write this from memory and explain each term.
    $$
    EAT = (1-p) \cdot t_{access} + p \cdot t_{fault\_service}
    $$
    Where $p$ is the page fault rate. The performance of the entire system is dominated by this equation.

4.  **First Principles Pathway:** If you forget the steps, rebuild them. The goal is to make a page on disk appear to be in memory for a program. What is the absolute minimum sequence?
    -   **Detection:** Something must notice the page isn't in RAM. (The MMU hardware trap).
    -   **Action:** The OS must get it from disk. (Disk I/O).
    -   **Placement:** The OS needs a place to put it. (Find a free frame).
    -   **Record-keeping:** The OS must update its records so the detection doesn't fail next time. (Update page table).
    -   **Resumption:** The program must be able to continue. (Restart the faulting instruction).

## Common mistakes
1.  **Page Fault vs. Segmentation Fault:** A page fault is a routine OS event to load data. A segmentation fault is a fatal error where a program tries to access a memory address it has no legal right to access. The OS's first step in the page fault handler is to check if the access is legal; if not, it turns the page fault into a segmentation fault.
2.  **Forgetting to Restart the Instruction:** The process must be transparent. If you don't restart the instruction that caused the fault, the program will fail or have incorrect data. Some complex instructions may need careful handling to be restarted correctly (e.g., a block copy instruction that was halfway done).
3.  **Ignoring OS Overhead:** When calculating page fault service time, students often just count the disk access time. You must also include the time to trap to the OS, run the handler code, update the page table, and context-switch. While disk I/O dominates, the other parts are not zero.
4.  **Assuming a Free Frame:** In any real system, memory is almost always full. The case where the OS must first run a *page replacement algorithm* (like LRU or Clock) to evict an existing page is the common case, not the exception. This adds another layer of complexity and time cost.
