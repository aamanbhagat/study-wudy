## 1. The one-sentence answer
A **watchdog timer** is an independent hardware counter that forces a system reset unless software periodically asserts a feed signal within a bounded interval.

Embedded systems run without human supervision and can enter unrecoverable states from cosmic-ray bit flips, stack overflows, or deadlocked tasks. The watchdog supplies an external enforcement mechanism: its counter runs on a separate clock domain and issues a reset pulse once it reaches its terminal count. Software must therefore demonstrate liveness by resetting the counter before that terminal count; failure to do so implies the processor is no longer executing the intended control flow.

This arrangement decouples the detection of failure from the very processor that may have failed. The result is a deterministic upper bound on the duration of any undetected hang.

> [!NOTE]
> The watchdog does not prevent bugs; it converts the unbounded recovery time of a crashed system into a bounded recovery time measured in milliseconds.

## 2. Why this matters — concrete and current
NASA’s Perseverance rover employs a triple-redundant watchdog architecture on its RAD750 processor; each missed feed triggers a hardware reset that restores the flight software to a known safe state within 200 ms, a requirement documented in JPL’s “Flight Software Fault Management” report (2021).

Automotive engine-control units from Bosch and Continental integrate windowed watchdogs that must be fed inside a 10–50 ms open window; violation aborts fuel injection and forces the vehicle into limp-home mode, satisfying ISO 26262 ASIL-D.

Modern pacemakers from Medtronic contain an on-chip watchdog that resets the pacing state machine if the real-time task scheduler misses its 8 ms deadline, preventing asystole caused by firmware deadlock.

SpaceX Starlink satellites use an external Maxim MAX823 watchdog whose timeout is set to 1.6 s; after repeated missed feeds the satellite powers down its phased-array radios and awaits ground-commanded recovery, limiting orbital debris risk.

Industrial PLCs from Siemens S7-1500 series embed a hardware watchdog that forces output modules to their safe state within 50 ms of processor failure, meeting IEC 61131-2 timing constraints for factory safety interlocks.

## 4. Building the idea — from intuition to formalism

### Step 1 — An independent counter
A free-running counter clocked from a source independent of the CPU measures elapsed time.  
Example: an 8-bit counter clocked at 1 kHz reaches 255 after 255 ms.  
Formal statement:  
$$C(t) = \lfloor t \cdot f_{\text{clk}} \rfloor \bmod 2^n$$  
> [!WARNING]  
> Using the CPU clock lets a halted processor stop the counter, defeating the mechanism.

### Step 2 — Timeout detection
When the counter reaches its terminal value, combinational logic asserts a reset request.  
Example: a 16-bit counter at 32 kHz yields a 2 s timeout.  
Formal statement:  
$$\text{reset} = 1 \iff C(t) = 2^n - 1$$  
> [!WARNING]  
> If the reset pulse width is shorter than the processor’s minimum reset assertion time, the device may ignore it.

### Step 3 — The feed operation
Software writes a specific key sequence to a control register, clearing the counter.  
Example: writing 0xA5 followed by 0x5A within one instruction cycle resets the count to zero.  
Formal statement:  
$$\text{feed} \implies C(t^+) = 0$$  
> [!WARNING]  
> A single write can be accidentally generated by runaway code; key sequences reduce that probability.

### Step 4 — Windowed versus simple timeout
A windowed watchdog adds a lower bound: feeds arriving too early are also treated as faults.  
Formal statement:  
$$\text{valid feed} \iff t_{\text{early}} < \Delta t < t_{\text{late}}$$  
> [!WARNING]  
> Simple watchdogs allow an infinite loop that feeds continuously, masking the underlying fault.

### Step 5 — External versus internal placement
An external watchdog IC receives its feed over a GPIO pin and drives the reset line directly.  
Formal statement:  
$$\text{reset}_{\text{ext}} = \neg\text{feed}(t) \land t > T_{\text{out}}$$  
> [!WARNING]  
> Internal watchdogs share silicon with the CPU and can be disabled by the same latch-up event that halts the processor.

## 5. Worked examples — every step shown

**Example 1 — Simple timeout calculation**  
*Given:* 12-bit counter, 125 kHz clock, required timeout 30 ms.  
*Find:* terminal count value.  
Count increments every \(8\,\mu\)s.  
Number of ticks needed: \(30 \times 10^{-3} / 8 \times 10^{-6} = 3750\).  
3750 in binary is 0xEA6 (12 bits).  
**0xEA6**  
*Reflection:* The calculation assumes the clock source is accurate; tolerance analysis belongs in a later example.

**Example 2 — Window violation**  
*Given:* windowed watchdog, open window 8–12 ms, feed issued at 3 ms.  
*Find:* outcome.  
3 ms lies before the lower bound.  
Logic asserts both “too early” and reset.  
**Reset asserted**  
*Reflection:* Early feeds are common when developers place the feed at the top of a fast loop.

**Example 3 — Missed feed under RTOS preemption**  
*Given:* 10 ms task period, watchdog timeout 15 ms, higher-priority ISR runs for 12 ms.  
*Find:* whether reset occurs.  
The low-priority task cannot feed until the ISR finishes.  
Elapsed time since last feed exceeds 15 ms.  
**Reset occurs**  
*Reflection:* Watchdog period must exceed worst-case interrupt latency plus task period.

**Example 4 — External watchdog with open-drain output**  
*Given:* MAX823, 1.6 s timeout, MCU GPIO drives WDI pin, reset connected to nRESET.  
*Find:* sequence after software deadlock.  
No edges appear on WDI for 1.6 s.  
Open-drain output pulls nRESET low for 200 ms.  
MCU restarts from vector table.  
**System recovers**  
*Reflection:* The external device continues operating after total CPU power collapse, unlike an internal watchdog.

## 6. Common traps and how to avoid them

| Trap                              | Why it happens                              | How to avoid it                                      |
|-----------------------------------|---------------------------------------------|------------------------------------------------------|
| Feeding inside an infinite loop   | Developer places feed at loop head for convenience | Move feed to end of verified execution path only     |
| Disabling watchdog in production  | “It interferes with debugging”              | Gate disable with a compile-time switch that is off in release builds |
| Shared clock domain               | Simpler schematic                           | Always select an independent low-power oscillator    |
| No tolerance analysis             | Nominal timeout meets spec on paper         | Add ±20 % guard band for crystal drift and voltage variation |
| Multiple feeds without state check| Code can feed even when tasks are dead      | Feed only after a health-status register passes CRC  |
| Reset pin not driven long enough  | External IC pulse width too short           | Verify datasheet t_RST(min) against processor spec   |
| Watchdog cleared by bootloader    | Bootloader runs before application starts   | Feed from bootloader or lengthen timeout during boot |

## 7. The textbook-precise statement
A watchdog timer is a hardware down-counter clocked by an autonomous oscillator that generates an asynchronous reset assertion when its count reaches zero and that can be reloaded to a non-zero value only by a correctly sequenced write from the supervised processor. The supervised interval \(T_{\text{sup}}\) must satisfy  
$$T_{\text{task}} + T_{\text{lat}} < T_{\text{sup}} < T_{\text{safe}}$$  
where \(T_{\text{task}}\) is the nominal scheduling period and \(T_{\text{safe}}\) is the maximum acceptable undetected fault duration. (Barr & Massa, *Programming Embedded Systems*, 2e, §6.4.)

## 9. The memory technique

**The hook** — Picture a loyal dog that barks and resets the house alarm unless you pat its head every few minutes; if you are unconscious the house resets itself.

**What to overlearn** — (1) Watchdog clock must be independent; (2) feed only after health verification; (3) windowed mode rejects both early and late feeds.

**Spaced-repetition schedule** — Review at 1 day, 3 days, 7 days, 16 days, 35 days.

**First-principles fallback** — Re-derive the required timeout from worst-case interrupt latency plus task period, then verify the clock source is autonomous.
