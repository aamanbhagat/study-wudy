## 1. The one-sentence answer
**Inline namespaces and anonymous namespaces are C++ constructs that respectively relax and restrict name lookup and linkage rules around ordinary namespaces.**

An anonymous namespace is written without a name and injects every declaration inside it into an unnamed namespace that is unique to the current translation unit. This forces internal linkage: the names cannot be seen from any other translation unit even if the header that contains the namespace is included elsewhere. Inline namespaces, introduced in C++11, are written with the keyword `inline` before the namespace name; they make every declaration inside them appear as if it were declared directly in the enclosing namespace for the purposes of argument-dependent lookup and unqualified name lookup, while still keeping the nested namespace for versioning.

The two features solve orthogonal problems. Anonymous namespaces hide implementation details at link time. Inline namespaces expose implementation details at compile time without breaking source compatibility across library versions.

> [!NOTE]
> The decisive difference is linkage versus lookup: anonymous namespaces affect the linker, inline namespaces affect the compiler’s name search.

## 2. Why this matters — concrete and current
The LLVM project places large portions of its C++ API inside inline namespaces such as `llvm::v13` so that a single header can ship symbols for multiple library versions while preserving ABI stability for downstream tools such as Clang and LLDB.

Google’s Abseil library uses anonymous namespaces inside `.cc` files to guarantee that helper classes and functions never collide with identically named entities in other translation units, eliminating whole classes of one-definition-rule violations reported by the build system.

NASA’s flight-software build for the Perseverance rover’s vision pipeline isolates low-level image-processing routines inside anonymous namespaces so that the same source files can be compiled into both the real-time partition and the ground-test harness without symbol clashes at final link time.

Semiconductor vendors such as Intel ship oneAPI Math Kernel Library headers that wrap architecture-specific kernels in inline namespaces (`mkl::vml::avx512`) so that a single include directory works for both AVX2 and AVX-512 targets selected at compile time.

## 4. Building the idea — from intuition to formalism

### Step 1 — Namespaces already partition the global scope
A namespace declaration creates a new scope whose members are accessed with the `::` operator or via `using` directives.  
```cpp
namespace math { double sqrt(double); }
```
The formal statement is that the name `math::sqrt` is distinct from any other `sqrt` in a different namespace.

> [!WARNING]
> Forgetting that namespace scope is declarative, not imperative, leads to the mistaken belief that re-opening a namespace in another file automatically merges definitions across translation units.

### Step 2 — Anonymous namespaces create a translation-unit-local scope
Writing `namespace { … }` is equivalent to `namespace __unique_per_TU { … }` where `__unique_per_TU` is a name generated by the compiler and never written by the user. All names inside receive internal linkage.

### Step 3 — Internal linkage prevents cross-TU visibility
Because the generated name differs in every translation unit, the same identifier declared in two anonymous namespaces denotes two distinct entities at link time. The ODR is therefore satisfied automatically.

### Step 4 — Inline namespaces extend lookup without changing linkage
Prefixing a namespace with `inline` makes its members visible to unqualified and ADL lookup as if they were members of the enclosing namespace, yet the members still reside in the nested scope for explicit qualification.

### Step 5 — The interaction with ADL is the key semantic change
When a function call’s arguments belong to a type defined inside an inline namespace, ADL considers both the inline namespace and its enclosing namespace. This is expressed by extending the set of associated namespaces in [basic.lookup.argdep].

### Step 6 — Versioning idiom follows directly
A library author can write
```cpp
namespace lib {
  inline namespace v2 { … }
}
```
so that `lib::foo` finds `lib::v2::foo` without source changes when the inline namespace is later renamed to `v3`.

### Step 7 — Textbook statement of the combined rule
A declaration `D` inside an inline namespace `N` that is a direct member of namespace `M` is also considered a member of `M` for the purposes of unqualified lookup and ADL, while its linkage remains unchanged. A declaration inside an anonymous namespace has internal linkage and a unique namespace name per translation unit.

## 5. Worked examples — every step shown

**Example 1 — Internal linkage via anonymous namespace**  
*Given:* Two translation units each contain  
```cpp
namespace { int x = 1; }
int get() { return x; }
```  
*Find:* Linker behaviour.  
Step 1: Each TU receives its own `__anon1::x` and `__anon2::x`.  
*Why* — the compiler manufactures distinct names.  
Step 2: `get` in TU1 returns `__anon1::x`.  
*Why* — ordinary unqualified lookup inside the TU.  
Step 3: At link time the two `x` symbols never collide.  
**Final answer**  
Two distinct objects exist; no ODR violation.

*Reflection* — The trick is remembering that the anonymous namespace is not “global”; it is per-TU.

**Example 2 — ADL through inline namespace**  
*Given:*  
```cpp
namespace lib { inline namespace v1 { struct S{}; void f(S); } }
lib::S s; f(s);
```  
*Find:* Whether `f` is found.  
Step 1: `S`’s associated namespaces include `lib::v1`.  
*Why* — inline namespace rule.  
Step 2: ADL therefore examines `lib` and `lib::v1`.  
*Why* — extended associated-namespace set.  
**Final answer**  
`lib::v1::f` is called.

*Reflection* — The call succeeds without `using` or qualification.

**Example 3 — Version switch**  
*Given:* Header declares `inline namespace v2` containing `struct Config`.  
*Find:* Effect of changing to `v3`.  
Step 1: All code that wrote `lib::Config` continues to compile.  
*Why* — lookup still reaches the new inline namespace.  
**Final answer**  
ABI break is isolated to the mangled name `lib::v3::Config`.

*Reflection* — Source compatibility is preserved while binary compatibility is deliberately changed.

**Example 4 — Mixing both features**  
*Given:*  
```cpp
namespace lib {
  inline namespace v1 {
    namespace { void impl(); }
  }
}
```  
*Find:* Visibility of `impl`.  
Step 1: `impl` has internal linkage because of the anonymous namespace.  
*Why* — anonymous namespace rule takes precedence.  
Step 2: `impl` is still found by ADL from types in `lib::v1`.  
*Why* — inline namespace extends lookup.  
**Final answer**  
`impl` is hidden from other TUs yet participates in ADL inside its TU.

*Reflection* — The two mechanisms compose without conflict.

## 6. Common traps and how to avoid them

| Trap | Why it happens | How to avoid it |
|------|----------------|-----------------|
| Placing non-inline definitions in an anonymous namespace inside a header | The header is included in many TUs, each generating a separate copy | Move definitions to `.cpp` files or use `inline` functions |
| Expecting `inline namespace` to change linkage | The keyword only affects lookup, not storage duration or linkage | Remember the orthogonal axes: lookup vs. linkage |
| Using anonymous namespace for constants that must be shared | Internal linkage creates separate objects per TU | Use `inline constexpr` or external linkage |
| Forgetting that nested inline namespaces remain distinct for explicit qualification | `lib::v2::foo` is still a valid path | Always qualify explicitly when versioning is intentional |
| Defining a function template in an anonymous namespace and expecting it to be selected by ADL | The template is invisible outside its TU | Move such templates into named inline namespaces if ADL is required |
| Re-opening an anonymous namespace across multiple headers | Each header produces a different generated name | Never re-open anonymous namespaces; they are TU-local by design |
| Assuming `inline` on a namespace implies `inline` on its functions | The two uses of `inline` are unrelated keywords | Use `inline` on functions separately when needed for ODR |

## 7. The textbook-precise statement
An anonymous namespace definition has the form `namespace { member-specification }` and behaves as if the namespace had a unique name generated by the implementation; every name declared inside has internal linkage ([basic.link]/4, C++23). An inline namespace is declared with `inline namespace identifier { member-specification }`; its members are injected into the enclosing namespace for unqualified name lookup and ADL while retaining their original scope for all other purposes ([namespace.def]/8). See ISO/IEC 14882:2023 §9.8.2 and §6.6.4.

## 9. The memory technique

1. **The hook** — Picture an anonymous namespace as a locked room whose key is thrown away after the TU is compiled; an inline namespace as a glass wall that lets you reach inside without opening the door.
2. **What to overlearn** — (a) anonymous namespace ⇒ internal linkage, (b) inline namespace ⇒ lookup injection only, (c) the two features are orthogonal.
3. **Spaced-repetition schedule** — Review the linkage rule after 1 day, the ADL rule after 3 days, both together after 7 days, a full worked example after 16 days, and the textbook paragraph after 35 days.
4. **First-principles fallback** — Re-derive by asking: “Does this name need to be visible to the linker?” If no, use anonymous; if yes but you still want source compatibility across versions, use inline.

## 10. What this unlocks
Mastery of these two namespace forms lets you design versioned library interfaces and eliminate ODR violations without macros. The next concepts that rest directly on this foundation are:

- Namespace aliasing combined with inline namespaces for ABI versioning
- `inline constexpr` variables inside inline namespaces
- Module interface units that export inline namespaces
- Implementation of the `std::literals` inline namespace in the standard library
