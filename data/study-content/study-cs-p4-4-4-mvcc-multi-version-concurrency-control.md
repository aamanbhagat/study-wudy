## 1. What it is — in plain English

Imagine you're working on a shared document, like a Google Doc. If someone else is making big changes, you don't want to see their half-finished sentences or deleted paragraphs popping in and out of existence while you're trying to read. You want a stable view of the document.

Multi-Version Concurrency Control (MVCC) is like a clever system that lets many people read and write to a database at the same time without getting in each other's way. Instead of everyone looking at *the exact same live version* of a piece of data, MVCC makes copies.

When someone wants to change something, the database doesn't immediately overwrite the old data. Instead, it creates a *new version* of that data. Readers who started *before* the change was made will continue to see the *old version*, as if they're looking at a snapshot from the past. Readers who start *after* the change is complete will see the *new version*.

Think of it as a time-traveling database. Each person interacting with the database gets their own consistent view of the data, as it existed at a specific point in time (usually when they started their operation). This means readers never have to wait for writers, and writers usually don't have to wait for readers, making everything much faster and smoother.

## 2. Why it matters — real-world applications

MVCC is a cornerstone technology for many high-performance, highly concurrent database systems. Its ability to allow non-blocking reads is crucial for modern applications.

1.  **E-commerce Platforms (e.g., Amazon, Shopify):** Imagine millions of users browsing products, adding items to carts, and checking out, while inventory levels are constantly being updated by sellers or other customers. MVCC ensures that a customer browsing a product page sees a consistent price and stock level, even if another customer is simultaneously buying the last item or a seller is updating the description. Without MVCC, read operations would frequently block write operations (and vice-versa), leading to slow response times and a poor user experience during peak sales.

2.  **Financial Trading Systems (e.g., Stock Exchanges, High-Frequency Trading):** In these environments, market data (stock prices, order books) is updated thousands of times per second, while traders and automated algorithms are constantly querying this data to make buy/sell decisions. MVCC allows these systems to provide low-latency, consistent snapshots of market data to millions of concurrent observers without blocking critical write operations that update prices. This ensures that an algorithm making a decision based on a stock price sees a committed, stable value, not a price that's half-way through an update.

3.  **Collaborative Software Backends (e.g., Google Docs, Figma, Version Control Systems like Git):** While these applications often have their own specialized real-time collaboration protocols, the underlying databases that store the document history and metadata often leverage MVCC principles. When multiple users edit a document, MVCC helps manage the different versions of the document's state. When you "undo" a change, you're essentially reverting to an older version. When you see a document's history, you're looking at a sequence of versions. MVCC helps ensure that the database can efficiently store and retrieve these historical states while new edits are continuously being committed.

4.  **Scientific Data Processing & Machine Learning Pipelines (e.g., CERN, Aerospace Simulations):** Large-scale scientific experiments or simulations generate vast amounts of data that need to be stored, processed, and analyzed. Machine learning models might be trained on this data. MVCC can be critical in database systems supporting these efforts. For instance, if a physicist is running an analysis query on a dataset generated by a particle collider, they need to ensure their query operates on a consistent snapshot of the data, even as new experimental results are continuously being written to the database. In aerospace, simulations might generate terabytes of sensor data; an MVCC-enabled database allows engineers to query specific time slices of this data for fault analysis or performance tuning without blocking the ongoing data ingestion.

## 3. Prerequisites — what you must know first

Before diving deep into MVCC, ensure you have a solid grasp of these foundational database concepts:

*   **Transactions:** A sequence of operations performed as a single logical unit of work.
*   **ACID Properties:** The four key properties guaranteeing reliable transaction processing: Atomicity (all or nothing), Consistency (valid state), Isolation (concurrent transactions don't interfere), Durability (committed changes persist).
*   **Concurrency Control:** The general problem of managing simultaneous operations on a database to ensure correctness and efficiency.
*   **Locking Mechanisms:** Traditional methods like Two-Phase Locking (2PL) where transactions acquire locks on data items to prevent conflicts.
*   **Isolation Levels (SQL Standard):** Different degrees to which transactions are isolated from each other (Read Uncommitted, Read Committed, Repeatable Read, Serializable), and the anomalies they prevent (dirty reads, non-repeatable reads, phantom reads). MVCC is primarily concerned with achieving higher isolation levels like Repeatable Read or Snapshot Isolation.
*   **Database States:** How data evolves through time with committed and uncommitted changes.

## 4. The core idea — step by step

Let's break down MVCC, building it up piece by piece.

### Step 1: The Problem MVCC Solves

*   **Plain English:** Imagine a single bank account balance. If one person is trying to deposit money (a "write" operation) and another person is trying to check their balance (a "read" operation) at the exact same time, how do we make sure the reader doesn't see a temporary, incorrect balance, or that the writer doesn't get stuck waiting for the reader? Traditional systems often use "locks" which make one operation wait for the other, slowing things down.
*   **Concrete Example:**
    *   Account `A` has balance `$100`.
    *   Transaction $T_1$ starts: Reads `A`'s balance.
    *   Transaction $T_2$ starts: Deposits `$50` into `A`.
    *   If $T_1$ reads `A` *while* $T_2$ is updating it but hasn't committed yet, $T_1$ might see `$150` (a "dirty read") or `$100` (the old value) or even some intermediate, corrupted value. If $T_2$ locks `A` to update it, $T_1$ would have to wait.
*   **Formal/Mathematical Version:** Given a set of data items $D = \{d_1, d_2, ..., d_n\}$ and a set of concurrent transactions $T = \{T_1, T_2, ..., T_m\}$. The goal is to ensure that concurrent operations `read(d_i)` and `write(d_i, value)` maintain database consistency and transaction isolation without excessive blocking.
*   **What Could Go Wrong:**
    *   **Dirty Reads:** A transaction reads data written by an uncommitted transaction. If the uncommitted transaction later aborts, the read data becomes invalid.
    *   **Non-Repeatable Reads:** A transaction reads the same data item twice and gets different values because another committed transaction modified it in between.
    *   **Phantom Reads:** A transaction executes a query (e.g., `SELECT COUNT(*)`) and then re-executes the same query later, finding a different set of rows (e.g., more rows) because another committed transaction inserted new rows.

### Step 2: Multiple Versions of Data

*   **Plain English:** Instead of changing a piece of data directly in place, MVCC keeps *multiple copies* or "versions" of that data. When a transaction wants to update something, it doesn't overwrite the existing value; it creates a *brand new version* with the updated value. The old version still exists.
*   **Concrete Example:**
    *   Account `A` balance is `$100`. This is `A_v1`.
    *   Transaction $T_2$ wants to change `A`'s balance to `$150`. It doesn't modify `A_v1`. Instead, it creates `A_v2` with value `$150`. `A_v1` (value `$100`) still exists.
*   **Formal/Mathematical Version:** Each logical data item $X$ is represented by a sequence of physical versions $X = \langle x_1, x_2, \ldots, x_k \rangle$. Each version $x_i$ has a value $V_i$ and associated metadata, crucially including a `creation_timestamp` (or `TxID` of the transaction that created it) and a `deletion_timestamp` (or `TxID` of the transaction that "logically" deleted it by creating a newer version).
    $$ x_i = (V_i, \text{creation\_TxID}_i, \text{deletion\_TxID}_i) $$
*   **What Could Go Wrong:** Storing multiple versions indefinitely would consume excessive storage space. A "garbage collection" mechanism is needed to eventually remove old, unused versions.

### Step 3: Transaction Timestamps (or IDs)

*   **Plain English:** Every transaction that starts gets a unique "start time" or a unique, ever-increasing ID. This ID acts like a timestamp and is crucial for determining which version of data a transaction should see.
*   **Concrete Example:**
    *   Transaction $T_1$ starts at time `100`. Its `start_TxID` is `100`.
    *   Transaction $T_2$ starts at time `110`. Its `start_TxID` is `110`.
    *   Transaction $T_3$ starts at time `120`. Its `start_TxID` is `120`.
*   **Formal/Mathematical Version:** For each transaction $T_j$, the system assigns a unique transaction identifier $\text{TxID}_j$. This $\text{TxID}_j$ is typically assigned at the beginning of the transaction and represents its logical start time.
    $$ T_j \rightarrow \text{start\_TxID}_j \in \mathbb{N} $$
    (where $\mathbb{N}$ is the set of natural numbers, representing an increasing sequence).
*   **What Could Go Wrong:** Generating unique, monotonically increasing IDs efficiently in a distributed database system can be challenging. Clock synchronization becomes a concern if physical timestamps are used directly.

### Step 4: The Read Rule (Snapshot Isolation)

*   **Plain English:** When a transaction wants to read a piece of data, it doesn't just grab the latest version. Instead, it looks for the *latest committed version* of that data item that existed *before the reader's own start time*. This gives the transaction a consistent "snapshot" of the database as it was when the transaction began.
*   **Concrete Example:**
    *   Account `A` has `A_v1` (value `$100`, created by $T_0$ at `TxID=0`, committed at `TxID=0`).
    *   Transaction $T_2$ (start `TxID=110`) updates `A` to `$150`, creating `A_v2` (created by $T_2$ at `TxID=110`). $T_2$ commits at `TxID=115`.
    *   Transaction $T_1$ (start `TxID=100`) wants to read `A`. It looks for versions committed *before* `TxID=100`. It finds `A_v1` (committed at `0`). It *does not* see `A_v2` because `A_v2` was created *after* $T_1$ started (even though $T_2$ committed before $T_1$ tries to read).
    *   Transaction $T_3$ (start `TxID=120`) wants to read `A`. It looks for versions committed *before* `TxID=120`. It finds `A_v2` (committed at `115`). It sees `$150`.
*   **Formal/Mathematical Version:** A transaction $T_j$ with $\text{start\_TxID}_j$ attempting to read data item $X$ will select the version $x_k = (V_k, \text{creation\_TxID}_k, \text{deletion\_TxID}_k)$ such that:
    1.  $x_k$ was created by a transaction that committed *before* $T_j$ started: $\text{creation\_TxID}_k < \text{start\_TxID}_j$.
    2.  $x_k$ was not logically deleted by a transaction that committed *before* $T_j$ started: $\text{deletion\_TxID}_k \ge \text{start\_TxID}_j$ (or $\text{deletion\_TxID}_k$ is null/uncommitted).
    3.  Among all versions satisfying (1) and (2), $x_k$ is the one with the largest $\text{creation\_TxID}_k$.
    This rule ensures $T_j$ sees a consistent snapshot of the database as of its $\text{start\_TxID}_j$.
*   **What Could Go Wrong:** If the `creation_TxID` and `deletion_TxID` are not correctly managed with respect to transaction commit times, a reader might see an inconsistent state (e.g., a version that was logically deleted by a transaction that committed before the reader started).

### Step 5: The Write Rule (Creating New Versions)

*   **Plain English:** When a transaction wants to change a piece of data, it creates a *new version* of that data. This new version is initially "private" to the writing transaction. It only becomes visible to other transactions (those that start *after* the writing transaction commits) once the writing transaction successfully finishes and commits its changes.
*   **Concrete Example:**
    *   Account `A` has `A_v1` (value `$100`, created by $T_0$ at `TxID=0`).
    *   Transaction $T_2$ (start `TxID=110`) wants to update `A`. It creates `A_v2` (value `$150`).
    *   At this point, `A_v2` is only visible to $T_2$. `A_v1` is still the "current" public version.
    *   When $T_2$ commits, `A_v2` becomes publicly available, and `A_v1` is marked as logically deleted by $T_2$ (i.e., its `deletion_TxID` is set to `110`).
*   **Formal/Mathematical Version:** When a transaction $T_j$ with $\text{start\_TxID}_j$ performs a `write(X, new\_value)` operation:
    1.  It first reads the latest visible version of $X$ according to its read rule (Step 4). Let this be $x_k$.
    2.  It creates a new version $x_{\text{new}} = (\text{new\_value}, \text{start\_TxID}_j, \text{NULL})$.
    3.  The `deletion_TxID` of the previous version $x_k$ is set to $\text{start\_TxID}_j$.
    4.  This new version $x_{\text{new}}$ is initially uncommitted. It becomes visible to other transactions only after $T_j$ successfully commits. Upon commit, $\text{start\_TxID}_j$ effectively becomes the `commit_TxID` for $x_{\text{new}}$.
*   **What Could Go Wrong:** Two transactions might try to update the "same" logical data item concurrently. This is a write-write conflict. MVCC systems typically handle this by using a "first updater wins" rule: the first transaction to successfully *prepare* its write (e.g., by checking if the version it read is still the latest one for its snapshot) gets to commit, and subsequent conflicting writers are aborted. This ensures serializability of writes.

### Step 6: Concurrency without Locks (for Readers) and Snapshot Isolation

*   **Plain English:** The beauty of MVCC is that readers never block writers, and writers never block readers. A reader simply picks an appropriate old version to look at, while a writer creates a new version without touching the old ones. Each transaction operates on its own consistent "snapshot" of the database. This allows for very high concurrency, especially for read-heavy workloads.
*   **Concrete Example:**
    *   Account `A` has `A_v1` (value `$100`).
    *   $T_1$ (start `TxID=100`) reads `A`. It sees `A_v1` (`$100`).
    *   *Simultaneously*, $T_2$ (start `TxID=110`) updates `A` to `$150`, creating `A_v2`. $T_2$ commits.
    *   $T_1$ continues its work. If it reads `A` again, it *still* sees `A_v1` (`$100`) because its snapshot is based on `TxID=100`. $T_1$ is completely unaffected by $T_2$'s update.
    *   A new transaction $T_3$ (start `TxID=120`) reads `A`. It sees `A_v2` (`$150`).
    *   No transaction waited for another.
*   **Formal/Mathematical Version:** By ensuring each transaction $T_j$ reads only versions committed prior to its $\text{start\_TxID}_j$, MVCC provides **Snapshot Isolation**. This isolation level guarantees:
    1.  No Dirty Reads: Transactions only read committed data.
    2.  No Non-Repeatable Reads: A transaction always reads the same version of a data item throughout its execution, as determined by its snapshot.
    3.  No Phantom Reads: A transaction's queries always operate on the same set of rows determined by its snapshot.
    However, Snapshot Isolation does *not* guarantee full **Serializability** (the strongest isolation level). It can suffer from the **Write Skew anomaly**.
*   **What Could Go Wrong:** As mentioned, Write Skew. This occurs when two transactions read overlapping data, make decisions based on those reads, and then write to disjoint parts of that data, leading to an inconsistent state that would not be possible in a serial execution. Achieving full serializability with MVCC often requires additional validation checks (e.g., detecting if any data read by a transaction was subsequently written by another committed transaction before the current transaction attempts to commit).

Let's illustrate MVCC with a series of examples. Assume a simple database with one table `Accounts` and one column `balance`. We'll use `TxID` as our timestamp.

**Initial State:**
`Account_A`: `(value=100, creation_TxID=0, deletion_TxID=NULL)`

### Example 1: Basic Read-Write Concurrency

**Problem Statement:**
Transaction $T_1$ starts, reads `Account_A`'s balance.
Transaction $T_2$ starts, updates `Account_A`'s balance, and commits.
Transaction $T_1$ then reads `Account_A`'s balance again.
Transaction $T_3$ starts and reads `Account_A`'s balance.
Show what each transaction sees and explain why.

**Given:**
*   Initial `Account_A` state: `(value=100, creation_TxID=0, deletion_TxID=NULL)`
*   $T_1$: `start_TxID = 10`
*   $T_2$: `start_TxID = 20`, updates `Account_A` to `150`, commits at `commit_TxID = 25`
*   $T_3$: `start_TxID = 30`

**Goal:** Determine the value of `Account_A` seen by $T_1$ (first read), $T_1$ (second read), and $T_3$.

**Steps:**

1.  **$T_1$ starts:** `start_TxID = 10`.
    *   $T_1$ needs to read `Account_A`.
    *   **Rule:** Find version $x_k$ where `creation_TxID_k < 10` and `deletion_TxID_k >= 10` (or NULL), and `creation_TxID_k` is max.
    *   **Available versions:** `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)`
    *   `creation_TxID=0 < 10` (True)
    *   `deletion_TxID=NULL >= 10` (True, NULL is effectively $\infty$ for visibility)
    *   **$T_1$ sees `Account_A = 100`**
        *   *Explanation:* $T_1$ sees the initial version because it was created and committed before $T_1$ started, and no transaction committed *before* $T_1$ started had deleted it.

2.  **$T_2$ starts:** `start_TxID = 20`.
    *   $T_2$ wants to update `Account_A` to `150`.
    *   **Rule:** $T_2$ first reads `Account_A` according to its snapshot rule.
    *   **Available versions:** `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)`
    *   `creation_TxID=0 < 20` (True)
    *   `deletion_TxID=NULL >= 20` (True)
    *   $T_2$ sees `Account_A = 100`. This is the version it will logically update.
    *   **Rule:** Create a new version for the update.
    *   **New version:** `Account_A_v2 (value=150, creation_TxID=20, deletion_TxID=NULL)`
    *   **Rule:** Mark the old version as logically deleted by $T_2$.
    *   `Account_A_v1` is updated to `(value=100, creation_TxID=0, deletion_TxID=20)`
        *   *Explanation:* $T_2$ creates a new version. The `deletion_TxID` of `A_v1` is set to $T_2$'s `start_TxID` to signify that $T_2$ is creating a *newer* version. This new version `A_v2` is not yet committed.

3.  **$T_2$ commits:** `commit_TxID = 25`.
    *   The new version `Account_A_v2` is now committed.
        *   *Explanation:* The changes made by $T_2$ are now permanent and visible to future transactions.

4.  **$T_1$ reads `Account_A` again:** $T_1$'s `start_TxID` is still `10`.
    *   **Rule:** Find version $x_k$ where `creation_TxID_k < 10` and `deletion_TxID_k >= 10` (or NULL), and `creation_TxID_k` is max.
    *   **Available versions (after $T_2$ commit):**
        *   `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=20)`
        *   `Account_A_v2 (value=150, creation_TxID=20, deletion_TxID=NULL)`
    *   **Check `Account_A_v1`:**
        *   `creation_TxID=0 < 10` (True)
        *   `deletion_TxID=20 >= 10` (True)
        *   `Account_A_v1` is visible to $T_1$.
    *   **Check `Account_A_v2`:**
        *   `creation_TxID=20 < 10` (False)
        *   Therefore, `Account_A_v2` is NOT visible to $T_1$.
    *   **$T_1$ sees `Account_A = 100`**
        *   *Explanation:* $T_1$ continues to see its initial snapshot. Even though $T_2$ has committed, $T_1$'s `start_TxID` of `10` dictates that it cannot see any versions created by transactions that started *after* `10`. This prevents non-repeatable reads for $T_1$.

5.  **$T_3$ starts:** `start_TxID = 30`.
    *   $T_3$ needs to read `Account_A`.
    *   **Rule:** Find version $x_k$ where `creation_TxID_k < 30` and `deletion_TxID_k >= 30` (or NULL), and `creation_TxID_k` is max.
    *   **Available versions:**
        *   `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=20)`
        *   `Account_A_v2 (value=150, creation_TxID=20, deletion_TxID=NULL)`
    *   **Check `Account_A_v1`:**
        *   `creation_TxID=0 < 30` (True)
        *   `deletion_TxID=20 >= 30` (False)
        *   Therefore, `Account_A_v1` is NOT visible to $T_3$ (it was logically deleted by a transaction that started before $T_3$).
    *   **Check `Account_A_v2`:**
        *   `creation_TxID=20 < 30` (True)
        *   `deletion_TxID=NULL >= 30` (True)
        *   `Account_A_v2` is visible to $T_3$.
    *   **$T_3$ sees `Account_A = 150`**
        *   *Explanation:* $T_3$ started after $T_2$ created and committed `A_v2`, and $T_2$ also "deleted" `A_v1` from the perspective of transactions starting after $T_2$. So $T_3$ sees the latest committed version relevant to its snapshot.

**Final Answer:**
*   $T_1$ (first read): **100**
*   $T_1$ (second read): **100**
*   $T_3$: **150**

**Reflection:** This example highlights how MVCC prevents non-repeatable reads for $T_1$ by ensuring it always sees its initial snapshot. It also shows how new transactions ($T_3$) see the latest committed state.

### Example 2: Write-Write Conflict (First Updater Wins)

**Problem Statement:**
Two transactions $T_1$ and $T_2$ start concurrently and both attempt to update `Account_A`.
$T_1$ updates `Account_A` to `200`.
$T_2$ updates `Account_A` to `300`.
Show how MVCC handles this conflict, assuming a "first updater wins" policy.

**Given:**
*   Initial `Account_A` state: `(value=100, creation_TxID=0, deletion_TxID=NULL)`
*   $T_1$: `start_TxID = 10`, updates `Account_A` to `200`, attempts to commit.
*   $T_2$: `start_TxID = 15`, updates `Account_A` to `300`, attempts to commit.

**Goal:** Determine the final committed value of `Account_A` and which transaction succeeds.

**Steps:**

1.  **$T_1$ starts:** `start_TxID = 10`.
    *   $T_1$ reads `Account_A`.
    *   **Rule:** Find version $x_k$ where `creation_TxID_k < 10` and `deletion_TxID_k >= 10` (or NULL), and `creation_TxID_k` is max.
    *   **Available versions:** `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)`
    *   $T_1$ sees `Account_A = 100`. (This is its "read set" for validation later).
    *   $T_1$ creates `Account_A_v2 (value=200, creation_TxID=10, deletion_TxID=NULL)`.
    *   $T_1$ logically marks `Account_A_v1` for deletion by $T_1$: `(value=100, creation_TxID=0, deletion_TxID=10)`.
        *   *Explanation:* $T_1$ creates its own private version.

2.  **$T_2$ starts:** `start_TxID = 15`.
    *   $T_2$ reads `Account_A`.
    *   **Rule:** Find version $x_k$ where `creation_TxID_k < 15` and `deletion_TxID_k >= 15` (or NULL), and `creation_TxID_k` is max.
    *   **Available versions:**
        *   `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=10)` (note $T_1$ hasn't committed yet, so $T_1$'s deletion is not "public" yet).
        *   `Account_A_v2 (value=200, creation_TxID=10, deletion_TxID=NULL)` (not committed, so invisible to $T_2$).
    *   **Check `Account_A_v1`:**
        *   `creation_TxID=0 < 15` (True)
        *   `deletion_TxID=10 >= 15` (False - this is the key. Since $T_1$ hasn't committed, its `deletion_TxID` is not yet effective for other transactions' read rules. For $T_2$, `A_v1` is still visible, as $T_1$'s write is not yet committed.)
        *   *Correction for strict MVCC:* A transaction only sees *committed* versions. So $T_2$ would see `Account_A_v1` if $T_1$ hadn't committed yet. The `deletion_TxID` of `10` set by $T_1$ is *provisional* and only becomes effective if $T_1$ commits. For $T_2$'s read rule, it ignores uncommitted `deletion_TxID`s.
        *   So, $T_2$ effectively sees `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)` for its read operation.
    *   $T_2$ sees `Account_A = 100`. (This is its "read set" for validation later).
    *   $T_2$ creates `Account_A_v3 (value=300, creation_TxID=15, deletion_TxID=NULL)`.
    *   $T_2$ logically marks `Account_A_v1` for deletion by $T_2$: `(value=100, creation_TxID=0, deletion_TxID=15)`.
        *   *Explanation:* $T_2$ also creates its own private version, basing it on the same initial `A_v1` as $T_1$.

3.  **$T_1$ attempts to commit.**
    *   **Validation (First Updater Wins):** Before committing, $T_1$ checks if the version of `Account_A` it *read* (`Account_A_v1`) is still the latest *committed* version for its snapshot. In other words, has any other transaction committed a write to `Account_A` that would invalidate $T_1$'s read set?
    *   At this point, no other transaction has committed a write to `Account_A`.
    *   $T_1$ successfully commits.
    *   The `deletion_TxID` of `Account_A_v1` is finalized to `10`.
    *   `Account_A_v2` (value `200`) becomes committed and visible.
    *   Current state:
        *   `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=10)`
        *   `Account_A_v2 (value=200, creation_TxID=10, deletion_TxID=NULL)`
        *   `Account_A_v3` (still uncommitted, private to $T_2$)
        *   *Explanation:* $T_1$ is the first to successfully commit its write to `Account_A`.

4.  **$T_2$ attempts to commit.**
    *   **Validation (First Updater Wins):** $T_2$ checks if the version of `Account_A` it *read* (`Account_A_v1`) is still the latest *committed* version for its snapshot.
    *   However, $T_1$ has now committed `Account_A_v2` (created by `TxID=10`).
    *   The version that $T_2$ read (`Account_A_v1`, created by `TxID=0`) is no longer the latest *committed* version for transactions starting before $T_2$'s `start_TxID`. More precisely, $T_2$ needs to check if the version it based its update on (`A_v1`) has been updated by a *concurrent* transaction that committed.
    *   Since `Account_A_v2` (from $T_1$) has committed, and $T_1$ started *before* $T_2$ (or concurrently), $T_2$'s update conflicts.
    *   Therefore, $T_2$ fails its commit validation and **aborts**.
        *   *Explanation:* $T_2$ tried to update `Account_A` based on an outdated view. $T_1$ "won" the race to update `Account_A`. $T_2$'s changes are discarded.

**Final Answer:**
*   The final committed value of `Account_A` is **200**.
*   **$T_1$ succeeds**, **$T_2$ aborts**.

**Reflection:** This illustrates a common way MVCC handles write-write conflicts: by validating writes at commit time. The "first updater wins" (or "first committer wins") rule ensures that only one transaction's update based on a particular prior version succeeds, preventing lost updates.

### Example 3: Preventing Phantom Reads (with `WHERE` clause)

**Problem Statement:**
Consider a table `Products` with columns `product_id` and `category`.
Initial data:
`P_v1 (id=1, category='Electronics', creation_TxID=0, deletion_TxID=NULL)`
`P_v2 (id=2, category='Books', creation_TxID=0, deletion_TxID=NULL)`

Transaction $T_1$ starts, queries for all products in 'Electronics'.
Transaction $T_2$ starts, inserts a new product in 'Electronics', and commits.
Transaction $T_1$ then repeats its query.
Show how MVCC prevents $T_1$ from seeing the new product.

**Given:**
*   Initial `Products` table:
    *   `P_v1 (id=1, category='Electronics', creation_TxID=0, deletion_TxID=NULL)`
    *   `P_v2 (id=2, category='Books', creation_TxID=0, deletion_TxID=NULL)`
*   $T_1$: `start_TxID = 10`, query `SELECT * FROM Products WHERE category = 'Electronics'`.
*   $T_2$: `start_TxID = 20`, inserts `P_v3 (id=3, category='Electronics')`, commits at `commit_TxID = 25`.

**Goal:** Determine the results of $T_1$'s first and second queries.

**Steps:**

1.  **$T_1$ starts:** `start_TxID = 10`.
    *   $T_1$ executes `SELECT * FROM Products WHERE category = 'Electronics'`.
    *   **Rule:** For each row, $T_1$ finds the latest committed version visible to `TxID=10`.
    *   **Check `P_v1`:**
        *   `creation_TxID=0 < 10` (True)
        *   `deletion_TxID=NULL >= 10` (True)
        *   `category='Electronics'` (Matches `WHERE` clause).
        *   `P_v1` is visible to $T_1$.
    *   **Check `P_v2`:**
        *   `creation_TxID=0 < 10` (True)
        *   `deletion_TxID=NULL >= 10` (True)
        *   `category='Books'` (Does not match `WHERE` clause).
        *   `P_v2` is not returned.
    *   **$T_1$ (first query) result: `(id=1, category='Electronics')`**
        *   *Explanation:* $T_1$ sees only the existing product that matches its criteria, based on its snapshot.

2.  **$T_2$ starts:** `start_TxID = 20`.
    *   $T_2$ inserts a new product `(id=3, category='Electronics')`.
    *   **Rule:** An insert operation is essentially creating a new version of a "null" row.
    *   $T_2$ creates `P_v3 (id=3, category='Electronics', creation_TxID=20, deletion_TxID=NULL)`.
        *   *Explanation:* $T_2$ creates a new version for the inserted row. This version is private to $T_2$.

3.  **$T_2$ commits:** `commit_TxID = 25`.
    *   `P_v3` (value `(id=3, category='Electronics')`) becomes committed and visible to transactions starting *after* `25`.
        *   *Explanation:* The new product is now permanently in the database.

4.  **$T_1$ repeats its query:** `start_TxID = 10`.
    *   $T_1$ executes `SELECT * FROM Products WHERE category = 'Electronics'` again.
    *   **Rule:** For each row (including newly created ones), $T_1$ finds the latest committed version visible to `TxID=10`.
    *   **Check `P_v1`:**
        *   `creation_TxID=0 < 10` (True)
        *   `deletion_TxID=NULL >= 10` (True)
        *   `category='Electronics'` (Matches).
        *   `P_v1` is visible.
    *   **Check `P_v2`:** (Still not matching `WHERE` clause).
    *   **Check `P_v3`:**
        *   `creation_TxID=20 < 10` (False)
        *   Therefore, `P_v3` is NOT visible to $T_1$.
    *   **$T_1$ (second query) result: `(id=1, category='Electronics')`**
        *   *Explanation:* Even though `P_v3` has been committed, $T_1$'s snapshot is fixed at `TxID=10`. It cannot see any data created by transactions that started *after* `TxID=10`. This successfully prevents a phantom read for $T_1$.

**Final Answer:**
*   $T_1$ (first query): **`(id=1, category='Electronics')`**
*   $T_1$ (second query): **`(id=1, category='Electronics')`**

**Reflection:** This example demonstrates how MVCC, by fixing a transaction's view to a snapshot based on its `start_TxID`, effectively prevents phantom reads. New rows inserted by other transactions are simply not visible to the current transaction if they were created after its snapshot time.

### Example 4: Write Skew Anomaly (and how MVCC alone might allow it)

**Problem Statement:**
Consider two bank accounts, `Account_A` and `Account_B`, both initially with `$100` balance.
Constraint: The sum of balances `A + B` must always be greater than or equal to `$0`.
Transaction $T_1$ checks `A+B`, finds it's `$200` (which is $\ge 0$), then withdraws `$100` from `Account_A`.
Transaction $T_2$ checks `A+B`, finds it's `$200` (which is $\ge 0$), then withdraws `$100` from `Account_B`.
Both transactions commit.
Show how MVCC (with Snapshot Isolation) might allow this to happen, violating the business constraint.

**Given:**
*   Initial `Account_A`: `(value=100, creation_TxID=0, deletion_TxID=NULL)`
*   Initial `Account_B`: `(value=100, creation_TxID=0, deletion_TxID=NULL)`
*   Constraint: `A.balance + B.balance >= 0`
*   $T_1$: `start_TxID = 10`
    1.  Read `Account_A.balance`, `Account_B.balance`.
    2.  Check `A.balance + B.balance >= 0`.
    3.  Set `Account_A.balance = Account_A.balance - 100`.
    4.  Commit.
*   $T_2$: `start_TxID = 20`
    1.  Read `Account_A.balance`, `Account_B.balance`.
    2.  Check `A.balance + B.balance >= 0`.
    3.  Set `Account_B.balance = Account_B.balance - 100`.
    4.  Commit.

**Goal:** Determine the final balances of `Account_A` and `Account_B` and if the constraint is violated.

**Steps:**

1.  **$T_1$ starts:** `start_TxID = 10`.
    *   $T_1$ reads `Account_A` and `Account_B`.
    *   **Rule:** For `TxID=10`, find latest committed versions.
    *   `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)` is visible.
    *   `Account_B_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)` is visible.
    *   $T_1$ sees `A = 100`, `B = 100`.
    *   **Check:** `100 + 100 = 200 >= 0` (True).
    *   $T_1$ updates `Account_A`: creates `Account_A_v2 (value=0, creation_TxID=10, deletion_TxID=NULL)`.
    *   `Account_A_v1` is marked for deletion by $T_1$: `(value=100, creation_TxID=0, deletion_TxID=10)`.
        *   *Explanation:* $T_1$ reads a consistent snapshot and makes its decision.

2.  **$T_2$ starts:** `start_TxID = 20`.
    *   $T_2$ reads `Account_A` and `Account_B`.
    *   **Rule:** For `TxID=20`, find latest committed versions.
    *   At this point, $T_1$ has not committed. So `Account_A_v2` is not committed. `Account_A_v1`'s `deletion_TxID=10` is not yet effective for $T_2$'s read rule.
    *   `Account_A_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)` is visible to $T_2$.
    *   `Account_B_v1 (value=100, creation_TxID=0, deletion_TxID=NULL)` is visible to $T_2$.
    *   $T_2$ sees `A = 100`, `B = 100`.
    *   **Check:** `100 + 100 = 200 >= 0` (True).
    *   $T_2$ updates `Account_B`: creates `Account_B_v2 (value=0, creation_TxID=20, deletion_TxID=NULL)`.
    *   `Account_B_v1` is marked for deletion by $T_2$: `(value=100, creation_TxID=0, deletion_TxID=20)`.
        *   *Explanation:* $T_2$ also reads a consistent snapshot, *which is the same as $T_1$'s snapshot* because $T_1$ hasn't committed yet. It also makes its decision based on this.

3.  **$T_1$ attempts to commit.**
    *   **Validation:** $T_1$ checks if any data it *read* (`Account_A_v1`, `Account_B_v1`) has been updated by a *concurrently committed* transaction.
    *   No other transaction has committed yet.
    *   $T_1$ successfully commits.
    *   `Account_A_v1`'s `deletion_TxID` finalized to `10`.
    *   `Account_A_v2` (value `0`) becomes committed and visible.
        *   *Explanation:* $T_1$ commits successfully.

4.  **$T_2$ attempts to commit.**
    *   **Validation:** $T_2$ checks if any data it *read* (`Account_A_v1`, `Account_B_v1`) has been updated by a *concurrently committed* transaction.
    *   `Account_A_v1` was read by $T_2$. `Account_A` has now been updated by $T_1$ (which committed `Account_A_v2`).
    *   However, `Account_A_v1` was *not* in $T_2$'s *write set*. $T_2$ only modified `Account_B`.
    *   In pure Snapshot Isolation (which MVCC provides), write-write conflicts on the *same data item* are detected (as in Example 2). But a write skew involves transactions reading *overlapping* data and writing to *disjoint* data.
    *   Since $T_2$ did not write to `Account_A` (which $T_1$ updated), and $T_1$ did not write to `Account_B` (which $T_2$ updated), **no direct write-write conflict is detected by basic MVCC validation.**
    *   $T_2$ successfully commits.
    *   `Account_B_v1`'s `deletion_TxID` finalized to `20`.
    *   `Account_B_v2` (value `0`) becomes committed and visible.
        *   *Explanation:* $T_2$ also commits successfully because its writes don't directly conflict with $T_1$'s writes.

**Final State:**
*   `Account_A`: `(value=0, creation_TxID=10, deletion_TxID=NULL)` (from $T_1$)
*   `Account_B`: `(value=0, creation_TxID=20, deletion_TxID=NULL)` (from $T_2$)

**Final Answer:**
*   `Account_A` balance: **0**
*   `Account_B` balance: **0**
*   Constraint `A.balance + B.balance >= 0`: `0 + 0 = 0 >= 0`. **The constraint is NOT violated.**

**Reflection (Self-Correction/Clarification):** My initial setup for the write skew example was slightly off. The standard write skew anomaly *does* violate a constraint. Let's re-evaluate the constraint `A+B >= 0`. In this specific example, the final sum is 0, which *does* satisfy the constraint.

A more classic write skew example involves a constraint like "at least one account must have a positive balance" or "the sum must be greater than some positive threshold."

Let's adjust the problem for a clearer write skew scenario:
**Revised Constraint:** `A.balance + B.balance` must always be `> 0`. (i.e., you cannot empty *both* accounts).

**Revised Problem Statement (Hard):**
Initial state: `A=100, B=100`.
Constraint: `A+B > 0`.
$T_1$: reads A, B. If `A+B > 0`, then sets `A = 0`. Commits.
$T_2$: reads A, B. If `A+B > 0`, then sets `B = 0`. Commits.

**Steps (Revised):**

1.  **$T_1$ starts:** `start_TxID = 10`.
    *   $T_1$ reads `A=100`, `B=100`.
    *   **Check:** `100+100 = 200 > 0` (True).
    *   $T_1$ updates `A` to `0`. Creates `A_v2 (value=0, creation_TxID=10, deletion_TxID=NULL)`.
    *   `A_v1` marked `deletion_TxID=10`.

2.  **$T_2$ starts:** `start_TxID = 20`.
    *   $T_2$ reads `A=100`, `B=100` (since $T_1$ hasn't committed, its updates are not visible).
    *   **Check:** `100+100 = 200 > 0` (True).
    *   $T_2$ updates `B` to `0`. Creates `B_v2 (value=0, creation_TxID=20, deletion_TxID=NULL)`.
    *   `B_v1` marked `deletion_TxID=20`.

3.  **$T_1$ commits.**
    *   Validation: No conflicting writes to `A` or `B` from committed transactions.
    *   $T_1$ commits. `A_v2` (value `0`) is committed.

4.  **$T_2$ commits.**
    *   Validation: $T_2$ read `A_v1` and `B_v1`. It wrote to `B`.
    *   Has `A_v1` been updated by a concurrently committed transaction? Yes, $T_1$ updated `A` to `A_v2`.
    *   Does this invalidate $T_2$'s read set? In strict Snapshot Isolation, the validation typically checks only for write-write conflicts on the *same* item. Since $T_2$ did not write to `A`, and $T_1$ did not write to `B`, there is no *direct* write-write conflict.
    *   Therefore, under pure Snapshot Isolation, **$T_2$ commits successfully.**

**Final State (Revised):**
*   `Account_A`: `0`
*   `Account_B`: `0`
*   **Constraint `A+B > 0` is violated (`0+0 = 0`, which is not `> 0`).**

**Reflection on Revised Example:** This revised example clearly demonstrates the write skew anomaly. Both transactions read `A=100, B=100` and correctly deduce `A+B > 0`. $T_1$ then sets `A=0`, and $T_2$ sets `B=0`. Both commit because their writes are to *disjoint* data items (`A` and `B`), so MVCC's basic write conflict detection (first updater wins) doesn't catch it. However, the *combined effect* of their actions, based on the same initial snapshot, violates the integrity constraint. This is why Snapshot Isolation, while powerful, is not equivalent to full Serializability and often requires additional explicit locking or serializable snapshot isolation (SSI) mechanisms to prevent such anomalies.

## 6. Common mistakes and traps

1.  **Confusing MVCC with Locking:** Students often think MVCC is just another form of locking. MVCC *reduces* the need for locks, especially for readers, by providing multiple versions. It doesn't eliminate all locking, as writers might still need to acquire short-duration locks or perform validation to prevent write-write conflicts.
2.  **Assuming MVCC Automatically Provides Full Serializability:** MVCC typically provides Snapshot Isolation, which is a strong isolation level, but it is *not* equivalent to Serializability. The Write Skew anomaly is a classic example of a consistency issue that Snapshot Isolation allows but Serializability prevents.
3.  **Ignoring Garbage Collection of Old Versions:** While MVCC keeps multiple versions, it's not infinite. Old versions that are no longer visible to any active transaction must eventually be cleaned up. Forgetting this leads to unbounded storage growth and performance degradation.
4.  **Not Understanding the Difference Between Commit Timestamps and Transaction Start Timestamps:** A transaction's `start_TxID` determines its snapshot for reading. The `commit_TxID` (or the `start_TxID` of the transaction that created/deleted a version, upon commit) determines when a version becomes visible or effectively deleted to *other* transactions. Mixing these up leads to incorrect visibility rules.
5.  **Overlooking Write Skew:** This specific anomaly is a common blind spot. Students understand dirty reads, non-repeatable reads, and phantom reads, but write skew (where transactions read common data but write disjoint data, leading to an inconsistent state) is often missed.
6.  **Believing MVCC makes databases "eventually consistent":** MVCC is a strong consistency model (providing Snapshot Isolation or better within a single database). It's not about eventual consistency, which is a property often associated with distributed systems allowing temporary inconsistencies for higher availability.

## 7. Textbook-precise explanation

Multi-Version Concurrency Control (MVCC) is a concurrency control technique used in database management systems to provide transaction isolation by maintaining multiple versions of data items. Unlike traditional locking protocols that force transactions to wait for locks on data, MVCC allows read operations to proceed without blocking write operations, and vice-versa, by ensuring each transaction operates on a consistent snapshot of the database.

Formally, each data item $X$ in the database is represented by a set of versions, $V(X) = \{x_1, x_2, \ldots, x_k\}$. Each version $x_i$ of $X$ is a tuple:
$$ x_i = (\text{value}_i, \text{creation\_TxID}_i, \text{deletion\_TxID}_i) $$
where:
*   $\text{value}_i$ is the actual data content of the version.
*   $\text{creation\_TxID}_i$ is the unique transaction identifier (TxID) of the transaction that created this version. This TxID also serves as the logical `commit_timestamp` for this version once the creating transaction commits.
*   $\text{deletion\_TxID}_i$ is the TxID of the transaction that logically "deleted" this version by creating a newer version of the same logical data item. If the version is the most recent and has not been logically deleted, this value is `NULL` or $\infty$.

Each transaction $T_j$ is assigned a unique $\text{start\_TxID}_j$ upon its initiation. This $\text{start\_TxID}_j$ defines the transaction's consistent snapshot.

**Visibility Rule for Read Operations:**
A transaction $T_j$ with $\text{start\_TxID}_j$ attempting to read a data item $X$ will select the version $x_k \in V(X)$ such that:
1.  **Commit Visibility:** The transaction that created $x_k$ must have committed *before* $T_j$ started. This means $\text{creation\_TxID}_k < \text{start\_TxID}_j$. (Some implementations use $\le$ if $\text{start\_TxID}$ is also the `commit_TxID` for committed versions).
2.  **Deletion Visibility:** The version $x_k$ must not have been logically deleted by a transaction that committed *before* $T_j$ started. This means $\text{deletion\_TxID}_k \ge \text{start\_TxID}_j$ (or $\text{deletion\_TxID}_k$ is `NULL` or represents an uncommitted transaction).
3.  **Most Recent Committed Version:** Among all versions satisfying (1) and (2), $x_k$ is the one with the largest $\text{creation\_TxID}_k$.

**Rule for Write Operations:**
When a transaction $T_j$ with $\text{start\_TxID}_j$ performs a `write(X, new\_value)`:
1.  $T_j$ first identifies the current visible version of $X$ according to its read rule (let's call it $x_{\text{old}}$).
2.  It creates a new version $x_{\text{new}} = (\text{new\_value}, \text{start\_TxID}_j, \text{NULL})$. This version is initially uncommitted and visible only to $T_j$.
3.  The $\text{deletion\_TxID}$ of $x_{\text{old}}$ is set to $\text{start\_TxID}_j$.
4.  Upon $T_j$'s successful commit, $x_{\text{new}}$ becomes globally visible according to the read rule for other transactions, and the `deletion_TxID` of $x_{\text{old}}$ becomes effective.

**Conflict Resolution:**
*   **Read-Write Conflicts:** MVCC inherently resolves read-write conflicts without blocking. Readers simply access older versions, while writers create new versions.
*   **Write-Write Conflicts:** When two concurrent transactions attempt to write to the same logical data item, MVCC implementations typically employ a validation phase at commit time. A common strategy is "first updater wins" or "first committer wins," where the transaction that successfully commits its write first invalidates subsequent conflicting writes. A transaction $T_j$ attempting to commit a write to $X$ will check if the version of $X$ it read ($x_{\text{old}}$) is still the latest *committed* version for its snapshot. If another transaction has committed a newer version of $X$ since $T_j$ started, $T_j$ might be aborted to maintain consistency.

MVCC typically provides **Snapshot Isolation**, which prevents dirty reads, non-repeatable reads, and phantom reads. However, it does not guarantee full **Serializability** due to the possibility of the write skew anomaly. Achieving serializability with MVCC often requires additional mechanisms, such as Serializable Snapshot Isolation (SSI) or explicit predicate locking for specific constraints.
