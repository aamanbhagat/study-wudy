## 1. The one-sentence answer
**Operator precedence defines the strict evaluation order of operators inside any C expression so that the compiler never guesses.**

In C, every expression with more than one operator is parsed according to a fixed table rather than left-to-right scanning. The table ranks operators from highest precedence (postfix, unary) to lowest (comma), and each level also carries a fixed associativity (left-to-right or right-to-left). Without this rule set, the same source line would produce different results on different compilers.

The table is not arbitrary; it mirrors the hardware cost and mathematical grouping that programmers expect. Once internalised, you read any expression in C exactly as the compiler will evaluate it.

> [!NOTE]
> The single most important insight is that precedence is compile-time only; it never changes at runtime and cannot be overridden by parentheses alone when associativity also matters.

## 2. Why this matters — concrete and current
In the Linux kernel scheduler, the expression `task->prio += weight * (nice - 20)` relies on the exact precedence of `->`, `*`, `-`, and `+=`; a single misordering would corrupt process priorities on millions of servers.

NASA’s cFS flight software uses chained bit operations such as `reg = (val & MASK) | (new << SHIFT)` inside interrupt handlers; the precedence table guarantees that masking happens before shifting on radiation-hardened PowerPC cores.

In TensorFlow Lite Micro’s quantisation kernels, the line `scale = (qmax - qmin) / (fmax - fmin)` must evaluate subtractions before division; any deviation breaks fixed-point conversion on ARM Cortex-M devices used in edge ML.

The SQLite query planner rewrites expressions containing `a + b * c == d & MASK`; the C compiler’s precedence decisions directly affect the generated bytecode that runs on billions of phones and browsers.

The QEMU TCG intermediate representation evaluates `tmp = a ^ b & c + 1` thousands of times per second during dynamic binary translation; the precedence rules ensure identical results across x86, ARM, and RISC-V hosts.

## 4. Building the idea — from intuition to formalism

### Step 1 — Expressions are trees, not sequences
C never evaluates an expression strictly left to right when operators differ. The compiler first builds an abstract syntax tree whose shape is dictated solely by the precedence table.

Example: `a + b * c` becomes the tree `+(a, *(b, c))`.

Formal statement:  
$$E \to E_1 \oplus E_2 \quad \text{where precedence}(\oplus) \text{ decides grouping.}$$

> [!WARNING]
> Treating the source text as a flat list will silently produce wrong trees on every mixed-operator line.

### Step 2 — Highest precedence operators bind first
Postfix `++`, `--`, array `[]`, and function `()` sit at the top. They are applied before any unary or binary operator touches the same operand.

Example: `arr[i]++` is `(arr[i])++`, not `arr[(i++)]`.

Formal statement:  
$$\text{prec}([]) = \text{prec}(++) = 1 \quad (\text{highest}).$$

### Step 3 — Unary operators come next and are right-associative
`*`, `&`, `!`, `~`, unary `-`, `++`, `--` (prefix) and casts share precedence level 2 and associate right-to-left.

Example: `*p++` is `*(p++)`, not `(*p)++`.

Formal statement:  
$$ \text{unary} \to \text{unary } \text{op } E \quad (\text{right-to-left}). $$

> [!WARNING]
> Confusing prefix and postfix `++` associativity is the most frequent source of buffer overruns in pointer code.

### Step 4 — Multiplicative before additive
`*`, `/`, `%` bind tighter than `+` and `-`. Both groups associate left-to-right.

Example: `a + b * c / d` expands to `a + ((b * c) / d)`.

Formal statement:  
$$\text{prec}(*) > \text{prec}(+).$$

### Step 5 — Shifts, relational, equality, bitwise, logical, ternary, assignment, comma
Each subsequent level drops in precedence; the full order appears in the table below. Assignment operators are right-associative; the comma operator is left-associative and yields the rightmost value.

Formal statement (textbook form appears in section 7).

## 5. Worked examples — har step show karo

**Example 1 — Simple mixed arithmetic**  
*Given:* `int x = 2 + 3 * 4;`  
*Find:* value of `x`.  
Step 1: `*` has higher precedence than `+`.  
Step 2: `3 * 4` evaluates first → 12.  
Step 3: `2 + 12` → 14.  
*Why:* precedence rule forces multiplication before addition.  
**14**

*Reflection:* The example is tricky only because school PEMDAS intuition must be replaced by the C table; the result generalises to any additive-multiplicative mix.

**Example 2 — Pointer and postfix**  
*Given:* `int a[] = {10,20}; int *p = a; int v = *p++;`  
*Find:* values of `v` and `p`.  
Step 1: postfix `++` binds tighter than unary `*`.  
Step 2: `p++` yields old `p`, then increments.  
Step 3: `*` dereferences the old pointer → `v = 10`.  
*Why:* postfix has precedence 1, unary `*` has precedence 2.  
**v = 10, p now points to 20**

*Reflection:* Students often swap prefix/postfix; the tree shape decides which pointer is dereferenced.

**Example 3 — Assignment chain with bitwise**  
*Given:* `int x, y = 1; x = y & 3 + 2;`  
*Find:* value of `x`.  
Step 1: `+` precedes `&`.  
Step 2: `3 + 2` → 5.  
Step 3: `y & 5` → 1.  
Step 4: `=` assigns right-to-left (only one assignment here).  
*Why:* additive precedence 4 beats bitwise AND at level 8.  
**x = 1**

*Reflection:* The trap is assuming bitwise operators outrank arithmetic; they do not.

**Example 4 — Ternary and logical OR**  
*Given:* `int r = 0 || 1 ? 2 : 3;`  
*Find:* value of `r`.  
Step 1: `||` has lower precedence than `?:`.  
Step 2: `0 || 1` → 1 (true).  
Step 3: true selects 2 via ternary.  
*Why:* logical OR sits at precedence 12, ternary at 13.  
**r = 2**

*Reflection:* The expression is deliberately ambiguous in English; C removes ambiguity via the fixed table.

## 6. Common traps and how to avoid them

| Trap                              | Why it happens                              | How to avoid it                              |
|-----------------------------------|---------------------------------------------|----------------------------------------------|
| Believing `*p++` dereferences then increments | Postfix and unary share visual similarity   | Always draw the AST or add parentheses       |
| Placing `&` above `+`             | Bitwise operators feel “lower level”        | Memorise the single table line “additive > bitwise” |
| Forgetting assignment is right-associative | Most operators are left-associative         | Write `a=b=c` as `a=(b=c)` explicitly        |
| Using `==` and `=` in same expression without parens | Both have similar spelling                  | Never rely on precedence for equality vs assignment |
| Assuming comma has high precedence | Comma looks like argument separator         | Remember comma is lowest precedence operator |
| Ignoring cast precedence          | Cast looks like a function call             | Casts sit at unary level; parenthesise casts |
| Mixing shifts with relational     | `<<` visually precedes `<`                  | Check table: shifts (level 5) beat relational (level 6) |

## 7. The textbook-precise statement
In the C language, the precedence and associativity of operators are defined by the grammar in Kernighan & Ritchie, *The C Programming Language*, 2nd ed., Appendix A, §A7.2–A7.14. Each operator token belongs to exactly one of fifteen precedence levels; within a level, associativity is either left-to-right or right-to-left as specified. No operator may be redefined, and parentheses `( )` constitute the only mechanism to alter the default grouping. The resulting abstract syntax tree is evaluated according to the usual rules of value computation and side-effect sequencing.

Read the table top-down; higher number = lower precedence.

## 9. The memory technique
1. **The hook** — Picture a fifteen-floor hotel; operators on floor 1 (postfix) get served first, operators on floor 15 (comma) wait until last.
2. **What to overlearn** — The exact order of the fifteen levels plus the two right-associative groups (unary and assignment).
3. **Spaced-repetition schedule** — Review the table after 1 day, 3 days, 7 days, 16 days, 35 days.
4. **First-principles fallback** — When unsure, parenthesise every sub-expression and then remove parentheses only where the table already forces the same grouping.
